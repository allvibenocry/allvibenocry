### The root cause

Two things, one inside the other.

**The trigger, on the test host only: a shell in the test host's root cgroup
at boot.** The cgroup tree the test host booted with has no controllers for
its children:

```
/sys/fs/cgroup/cgroup.controllers:      cpuset cpu io memory hugetlb pids rdma
/sys/fs/cgroup/cgroup.subtree_control:  (empty)
/sys/fs/cgroup/system.slice/cgroup.controllers: (empty)
```

so no container's scope has a `pids.max` or a `memory.max`. The test host's
root cgroup holds processes of its own, which cgroup v2 forbids for any cgroup
that hands controllers to its children, the real root alone excepted:

```
26    start 05:09:46  /bin/sh      (parent 0: entered through docker exec)
4890  start 05:12:54  bash -l      (your host.mjs shell, 07:12:55 local)
```

Docker's API names pid 26 as exec session `0e6d34980910`: `/bin/sh`, with a
terminal and standard input, still running. No command on the workstation
started it (the only command-line session is your `host.mjs shell`), so it was
opened through Docker's API directly, **most likely by Docker Desktop's Exec
tab for the container, which opens exactly such a shell; you can say whether
it was open.** A `docker exec` joins the container's own cgroup, which, inside
the test host's private cgroup namespace, is its root; it arrived in the same
second the test host started, before systemd enabled the controllers, and from
then on the kernel refused to (containerd's line at 05:09:49.72). Every
container with a limit on processes or memory could then not start: **the
panel** (64 processes, 128 MB) and **its door** (64, 64 MB), and the agent's
three, had they been started. The proxy, the apps and their databases have no
limits, and came back. Your own shell, three minutes later, landed in the root
too, since nothing had been enabled to keep it out.

**This trigger cannot happen on a real machine**: there systemd's cgroup is
the real root, where processes are allowed and the controllers are always
enabled, and a `docker exec` joins the container's own scope. It is the stand-in
for a reboot that did not boot like a machine.

**The root cause, in the product: nothing brings back a container that Docker
failed to start.** Docker's restart policy (`unless-stopped`) restarts a
container that exits after it has run; a container whose start fails when the
daemon starts is left as it is, with the error in its state, and never tried
again. The engine writes the panel's door once, at its own start, and never
looks again; it never looks at the panel's own container at all. So **any**
failure at boot leaves the panel gone until someone runs `install.sh` again:
here a cgroup; on a real machine, for example, an address the home router has
not given yet when Docker publishes port 80 on it (the door is published on the
machine's address, not on every address; seen in item 2). doctor would have said it ("The control panel's container is
exited, and http://.../health answered nothing: run install.sh again"), and
nothing acts on what doctor says. So on a real machine the panel would not have
been gone after *every* restart, as the brief feared, but it would have been
gone after any restart where one thing was late, and would have stayed gone.
