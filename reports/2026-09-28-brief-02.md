## 1. Rollback and schema versions (D35)

**Built.**

- `src/lib/migrations.ts` splits a migration file into statements the way
  Postgres reads it (quotes, dollar quotes, nested comments) and classifies
  each: **additive** (new tables, non-unique indexes, nullable or defaulted
  columns without constraints, views, sequences, types, functions, comments,
  inserted rows) or **breaking** (drops, renames, type changes, new
  constraints, unique indexes, `not null` without a default, rewritten or
  deleted rows, `create or replace`, `do`, and **anything it does not
  recognise**).
- A breaking migration is released only when its file has a line of its own:
  `-- breaking: <what it changes>`.
- `release` has a new second step, before anything changes: every migration of
  the version prod runs is still there and unchanged, and every new one is
  additive or marked. Every release records the schema prod ran with, asked of
  the database's `schema_migrations`; v1 records its own at creation.
- `rollback` has a new step before deploying: it asks prod's database which
  migrations the older version does not know, reads each from the release
  that first brought it, and goes ahead across additive ones (saying which)
  or stops across a breaking one, naming it and pointing to `--restore-data`.
  A migration whose file is in no release counts as breaking.
- A release that fails after its breaking migration has run is recorded
  (`failed` in `project.json`), so that `rollback --restore-data` goes back
  from it with **its own** backup; `project status` says so.
- `project status` shows each database's schema. The walkthrough's
  unique-names migration now carries the mark.

**Run on the test host**, on one project (`gb`), in this order:

- An additive migration (`alter table entries add column mood text`) and code
  that writes it, released as v2: step `ok 2/14 … migrations/002_add_mood.sql:
  only adds`. One entry written on v2, then `allvibe rollback gb`:

  ```
  ok   2/5 prod's database is one v1 can run on
         one migration since v1, and it only adds, so v1 runs on it unchanged:
         migrations/002_add_mood.sql (released in v2): only adds
  …
  ok   5/5 prod answers its smoke check
         prod answers on v1: {"ok":true,"entries":3,"environment":"prod","version":"v1"}
  ```

  Before and after, the database said `3 entries, 1 with a mood`.
- A rename (`alter table entries rename column name to author`) without the
  mark: the release stopped at `FAIL 2/14 the migrations since v1 only add, or
  are marked breaking`, naming the file and the statement. A snapshot of
  project status, backups, images, tags and prod's image before and after was
  identical.
- The same file marked, released as v3; `allvibe rollback gb`:

  ```
  FAIL 2/5 prod's database is one v1 can run on
         v1 was not written for the database as it is now. Since v1, this migration has changed it in a way v1 cannot run on:
           migrations/003_name_to_author.sql (released in v3): it is marked breaking: renames name to author, and versions before it still read name
         Going back to v1's code alone would run it on data it does not understand, so this rollback stops here and nothing is changed.
  ```

  The snapshot before and after was identical, and prod still answered on v3.
  `--restore-data` without confirmation said `prod has 5 entries now; the
  backup has 4` and exited 2; with `--confirm-data-loss` it took a backup of
  prod first, restored the one from before v3, went back to v1 past the
  additive migration, and prod had `Ada, Bo, Cy, Di`, the entry written on v3
  gone from prod and kept in the backup taken first.
- Not in the brief's list, and tried because it was built: a marked breaking
  release (dropping the mood column) whose app then failed in prod (a health
  check made to fail above 3 entries, which prod had and dev did not). Its
  automatic rollback stopped at the schema step, the project recorded v4 as
  failed, a code rollback was refused again, and `rollback --restore-data
  --confirm-data-loss` restored **v4's own backup** (the one taken just before
  v4), not v3's, and went back to v1 with `Ada, Bo, Cy, Di`.

(The label "released in v2" was changed after this run to "from v2", and
"which failed" is added for a failed release; the walkthrough run below shows
the final wording.)

**Unit tests:** 8 for the classifier, among them the template's first
migration (additive), the walkthrough's unique-names migration (breaking, and
marked), keywords inside strings, and the mark. One of them caught a real bug

## 3. The key vault (D37)

**Built.** `allvibe key set <project> <dev|prod|agent> <NAME>` (the value
from standard input only), `key list <project>` (names, scopes, times, never
values), `key remove`. Each value is a file encrypted with `age` to the **same
two recipients as every backup**, the host key and the recovery key: no new
key to lose. Deploys decrypt an environment's keys into `/run/allvibe/keys/`
(a tmpfs) and mount each into the app at `/run/secrets/<NAME>`, the path in
`<NAME>_FILE`, never an environment variable. `allvibe-keys.service` puts them
back into memory at boot, before Docker (install.sh's new step 10; doctor
checks it). `key set` restarts the app with the key, and puts the old value
back if the app does not come up. Backups carry the vault beside the dump,
encrypted again; the restore check has a new step that proves every value in
it decrypts. `test/host/vault-check.sh` is the probe.

**Run on the test host**, with three random values made on the host (never
shown), for `recipes`: dev `WEATHER_API_KEY`, prod `WEATHER_API_KEY`, agent
`ANTHROPIC_API_KEY`.

  healthy; it finds the file's path in WEATHER_API_KEY_FILE`; `key list`
  showing names and times.
- Refused, exit 2 each, nothing changed: a value as an argument; a terminal on
  standard input (a real pty through `script`); a lower-case name; the scope
  `staging`.
- `sh vault-check.sh allvibe recipes …`: for each value, the count in command

## 4. Key check before commit (D38)

**Built.** `setup` takes gitleaks **8.30.1** out of the **same image, by the
same digest, as CI** uses, and checks the binary against its own pinned
checksum. Every project's repository gets a pre-commit hook (at creation,
before the first commit; by setup in existing projects; by every `dev
commit`) that runs it over what is staged, redacted, and says the file, the
line and the kind of key, never the value. It fails closed. `dev commit` shows
the message and unstages. `test/host/key-check.sh` is the probe; it makes its
fake key at random at run time, so no key shape is in this repository.

**Run on the test host**, in a scratch project:

```
== 1. allvibe dev commit, with a fake key on line 1 of config.js
FAIL 1/1 dev's changes committed
       Stopped: this commit has something in it that looks like a key or a password, so nothing was committed.

         config.js, line 1: looks like an Anthropic API key

       The value is not shown. A key never goes into the code: take it out of the file, put it in the key vault
         allvibe key set <project> <dev|prod> <NAME> < a-file-with-the-key
       and have the app read it from the file named in <NAME>_FILE. Then commit again.
exit 1
== 2. git commit, directly, as the agent does
Stopped: … config.js, line 1: looks like an Anthropic API key …
exit 1
== the fake key in any commit:                         0
== the fake key in any object, the staged copy included: 1
== after unstaging it and pruning, in any object:      0
== 3. a clean commit
       the key check found nothing that looks like a key
exit 0
== 4. with the scanner missing
       Stopped: the key check could not run, because its scanner is missing, so nothing was committed.
exit 1
```

**Seen, and worth knowing:** a stopped commit leaves the staged copy in git's
object store, unreferenced, until pruned (the `1` above): git writes it at `git
add`, before any hook runs. It was in no commit, and after unstaging and
`git prune` it was in no object. D38 records it.

**Unit tests:** 4 (the pinned image and checksum, the hook, the checker finding
the scanner on the host and in the agent's image, and reading only file, line
and rule).

**Not verified:** a commit with `--no-verify`, which is not checked by design
(D38); the key check before push comes with the GitHub integration.

## Appendix: the documents every new project gets

As `allvibe project create recipes` writes them on 2026-09-28.

### AGENTS.md

````markdown
# How to work on recipes

These are the instructions for any AI coding agent working in this project.
Read all of it before you change anything, and follow it every time.

## Who you are working for

The person you are working with may never have written code before. They
have an idea for an app, and they want to see it working. They cannot read
your code to check it, so they rely on what you tell them and on what they can
try with their own hands.

- **Explain everything in plain words.** No jargon. If a technical word cannot
  be avoided, say what it means the first time you use it.
- **Say what you are about to do before you do it,** and what you did after.
- **Never pretend.** If something did not work, or you are not sure it did, say
  so.

## Start with a plan

When the person tells you their idea, do not start building. First turn the
idea into **a short numbered plan**: a handful of small steps, each one
something they will be able to see or use.

**Every step has a check they can try themselves**: what to open, what to do,
and what they should see if it works. For example: "Open the guestbook, write
a message with an empty name, and press the button. You should see: Please
write your name."

Write the plan into `STATE.md`, show it to them, and ask whether it is what
they want. Change it until they say yes.

## Build one step at a time

Build **only the first step that is not done yet**. Keep each step small
enough that the person can try it in a minute or two.

## Stop after each step

When a step is built:

1. Commit it, with a message that says in plain words what changed.
2. Tell the person what you did, and give them the step's check.
3. Ask them to put the change into the test copy with
   `allvibe dev deploy recipes` (you cannot do that from where you
   work), and then to try the check.
4. **Stop, and wait** for them to tell you it works. Do not start the next step
   until they do. If it does not work, fix it, and ask them to try again.

A step is done when the person has tried it and it worked, not when you think
it is finished.

## Keep STATE.md and DECISIONS.md current

- `STATE.md` says where things stand: the plan, which steps are done (tried by
  the person), what is next, and anything you are waiting for them to do.
  Update it after every step.
- `DECISIONS.md` records every decision about the app with its reason, so that
  anyone who works on it later, you included, knows why things are the way they
  are. Add to it; never rewrite what is already there.

## Where you work, and what you can never reach

This project has two copies of the app:

- **dev**, the test copy, where you work. Its app answers at
  `http://allvibe-recipes-dev-app:3000/` and its database at
  `allvibe-recipes-dev-db:5432`. Nothing in it is real.
- **prod**, the real app, with the real data. **You can never reach it**, and
  that is on purpose. A change reaches prod only when the person releases it,
  and a release first makes a backup and proves the backup can be restored.

Keep `GET /healthz` answering `{"ok":true,...}` after it has read the database:
it is how every check, backup test and release knows the app works.

## Changing the database

The database changes only through **migrations**: numbered SQL files in
`migrations/`, applied once each, in order, when the app starts.

- **Add a new numbered file for every change.** Never edit or delete a
  migration that already exists: it may have run in prod.
- **Only add.** New tables, new columns that may be empty or have a default,
  new indexes. The version before yours must still work on the database after
  yours, so that going back to it never loses data.
- **Anything else is a breaking change**: dropping or renaming a table or a
  column, changing a column's type, a new rule the existing data may break
  (such as "each name only once"), or changing rows that are already there.
  Only make one if the person agrees, after you have explained, in plain words,
  that going back past this release will mean putting all the data back as it
  was before it, and losing whatever was written since. Then say so in the
  file, on a line of its own:

  ```sql
  -- breaking: <what it changes>
  ```

  A release refuses a breaking migration without that line.

## Keys and passwords

- **Never put a key, a password or any other secret in the code**, in the
  repository, in a commit message, or in anything you print.
- **Never ask the person to paste a key to you.** Ask them to put it in the key
  vault instead:

  ```sh
  allvibe key set recipes dev NAME_OF_THE_KEY < file-with-the-key
  ```

  (and `prod` for the real app's own value).
- **The app reads each key from a file**, whose path is in an environment
  variable with the key's name and `_FILE` after it. For a key called
  `WEATHER_API_KEY`:

  ```js
  import { readFileSync } from "node:fs";
  const weatherKey = readFileSync(process.env.WEATHER_API_KEY_FILE, "utf8").trim();
  ```

  The database password arrives the same way, as `DATABASE_PASSWORD_FILE`.
- Every commit is checked for anything that looks like a key, and stopped if it
  finds one. If that happens, take the key out of the code, and use the vault.

## Commits

Commit after every step, and only then ask the person to try it. Never rewrite
the history (`git reset --hard`, `git rebase`, `git commit --amend` on
something already committed), and never skip the key check (`--no-verify`).
````
