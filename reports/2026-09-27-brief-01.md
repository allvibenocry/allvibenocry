## 6. Backup and restore test

**Built.** `allvibe backup-target set|show`, `backup`, `backups`,
`restore-check`, `recovery-key status|confirm`, and the timer's
`scheduled-backup`.

- **A target must be provably off the machine** (D22): not on the root
  filesystem (which is also what an unplugged disk's mount point is), not on the
  filesystem or physical disk of the system or of Docker's data (found through
  partitions, LVM and LUKS), a real disk or a network share, and writable by the
  service user.
- **A backup** is `pg_dump` inside prod's own database container, streamed
  through `age` to the host key and the recovery key, written `.partial`, flushed
  and renamed, with a manifest last (D23).
- **A restore check** verifies the checksum, decrypts the whole file, restores
  it into a scratch database on a scratch internal network, runs the backed-up
  version of the app against it, asks its own `/healthz`, and removes
  everything. It never touches prod.
- **The timer** (03:30 plus up to 30 minutes, `Persistent=true`) is enabled by
  install and runs a backup and a restore check of that backup for every project;
  every run is recorded with its reason (D24).

**Ran and observed**, on a fresh test host. The root filesystem refused:

```
FAIL 1/2 the backup target is off this machine and writable
       /var/backups/allvibe is on this machine's own root filesystem, which is not off the machine
```

(Without the test override the backup volume itself is refused too, honestly:
"on the same filesystem as the data it would back up (/var/lib/docker)". And
before `chown`, "not writable by allvibe: EACCES".) Then:

```
ok   3/4 an encrypted backup of prod, on the target
       /mnt/allvibe-backup/allvibe/guestbook/guestbook-prod-20260926T224655Z.dump.age (3.7 kB, sha256 4b4bfd95a338…)
       encrypted to this machine's backup key and to the recovery key; prod v1, 2 entries when it was taken
…
ok   4/4 the app's own health check passes against the copy
       allvibe-guestbook:v1 against the restored copy: {"ok":true,"entries":2,"environment":"restore-check","version":"v1"}
       guestbook entries in the restored copy: 2 (prod had 2 when the backup was taken)
     the scratch copy, its network and the decrypted file are removed; prod was not touched
```

On the backup-target volume: the `.dump.age` and its `.json`, both mode 600,
owned by the service user. The file begins `age-encryption.org/v1`, and **the
recovery key alone decrypts it** (`pg_restore --list` showed both tables and
their data). `recovery-key confirm` accepted the right key, deleted the
on-machine copy, and refused a wrong one.

The timer: `enabled / active` right after install; `systemctl start
allvibe-backup.service` ran a backup and a restore check as the service user,
`Result=success`; with the backup volume unmounted the service failed
(`exit-code`), the run was recorded as `FAILED at "the backup target is off
this machine and writable": … on this machine's own root filesystem`, and
`doctor` showed it as a problem. After `node test/host/host.mjs restart`:
`enabled / active`, the volume mounted again, both backups on it, and `doctor`
green except the recovery key (unconfirmed on that fresh host, correctly).

**Not verified.** A real USB disk or NAS share, a real reboot, and a run that
the timer starts by itself at 03:30. All in STATE.md.

not to the one prod had actually run when the current one was released (they
differ after a rollback and a new release). Each release now records the
version it replaced, and rollback goes there; checked live (v4 released over v2,
rolled back to v2) and in unit tests. A crash-looping deploy now fails at once
instead of after a timeout, and the failure names the app's error line rather
than the end of a stack trace.

**Not verified.** On real hardware.
